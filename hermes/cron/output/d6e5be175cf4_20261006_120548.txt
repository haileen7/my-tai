## عنوان
`[improve] /api/todos write routes are gated by ability: (ANY) not abilities: (ALL) — a todos:read-only token can store, update, delete and toggle`

## یافته
`routes/api.php:165-173` هر شش مسیر `/api/todos` — دو GET و **چهار نوشتن** — را در یک گروه با یک بررسی توانایی گذاشته:

```php
Route::middleware(['ability:todos:read,todos:write', 'role_or_permission:calendar'])->group(function () {
    Route::get('/todos', ...);            // read
    Route::post('/todos', ...);           // write
    Route::put('/todos/{todo}', ...);     // write
    Route::delete('/todos/{todo}', ...);  // write
    Route::post('/todos/{todo}/toggle-complete', ...); // write
});
```

`ability:` یعنی `CheckForAnyAbility` که با **اولین** توانایی منطبق `return $next($request)` میکند. پس توکنی که فقط `todos:read` دارد از دروازه رد میشود و وارد `store`/`update`/`destroy`/`toggleComplete` میشود. کنترلر هم `tokenCan()` خودش ندارد — تنها لایهٔ اعمال، همین گروه مسیر است.

**اثبات اجرای واقعی** (بدون هیچ تغییری در ریپو):

```
DELETE api/todos/{todo}  ⇒ CheckForAnyAbility:todos:read,todos:write   ← همان بررسیِ مسیر خواندنی
```

و اجرای همان میدلور با توکنی که فقط `todos:read` دارد:

```
GET    /api/todos  ⇒ ALLOWED      PUT    /api/todos/1 ⇒ ALLOWED
POST   /api/todos  ⇒ ALLOWED      DELETE /api/todos/1 ⇒ ALLOWED
POST   /api/todos/1/toggle-complete ⇒ ALLOWED
```

گروهی که درست تفکیک شده، به‌عنوان شاهد مقایسه:

```
abilities:hardware:write  on DELETE  ⇒ 403 (blocked) — درست
```

`/api/todos` تنها گروه نوشتنی در کل `routes/api.php` است که لایهٔ `abilities:` ندارد. بقیه (`units`, `hardware`, `tickets`, `tickets/*/comments`, `persons`) هر دو لایه را دارند.

## اهمیت
قرارداد طراحی (`references/api-endpoints.md:41`) این است: گروه خواندنی `ability:*` (ANY)، گروه نوشتنی `abilities:*` (ALL). جدول `AGENTS.md:131` هم ستون نوشتن را «same middleware» ثبت کرده — پس هر ممیزی با خواندن اسناد نتیجه میگیرد نوشتن todo توانایی‌سنجی شده، که نیست.

**شدت صادقانه: نقص نهفته، نه تشدید فعال.** تنها محل صدور توانایی `User::getApiTokenAbilities()` (`app/Models/User.php:165-168`) است که `todos:read` و `todos:write` را با یک شرط `calendar` با هم میگذارد، پس توکن `POST /api/login` نمیتواند یکی را بدون دیگری داشته باشد. به محض تفکیک گرانتر — همان جهتی که #690 و #784 در پیش گرفتند — یا صدور توکن بیرون از آن تابع، فعال میشود.

اینکه برای فعال شدن به تغییر دوم نیاز دارد دقیقاً دلیل بقایش است: هیچ تستی آن را تثبیت نمیکند. `ApiAbilityTest.php:249-271` فقط با `['todos:read']` یا `['todos:write']` **GET** میزند؛ هیچ تستی توکن تک‌توانایی را روی مسیر **نوشتنی** امتحان نمیکند.

## اقدام پیشنهادی
- گروه را مثل `hardware` تفکیک کنید: گروه بیرونی `ability:todos:read,todos:write` و گروه تو‌در‌تو `abilities:todos:write` برای چهار مسیر نوشتنی.
- `AGENTS.md:131` را اصلاح کنید — ستون نوشتن باید `abilities:todos:write` باشد نه «same middleware».
- تست‌های رگرسیون جاافتاده در `ApiAbilityTest.php`: توکن `['todos:read']` + `calendar` باید روی هر چهار مسیر نوشتنی **403** بگیرد در حالی که `GET /api/todos` همچنان **200** است؛ توکن `['todos:write']` باید موفق شود.
- همان بازبینی را روی `POST /api/notifications/{id}/read` و `read-all` هم بزنید — آن‌ها هم زیر `ability:notifications:read` وضعیت را تغییر میدهند. چون `notifications:write` تعریف نشده، این یکی تصمیم محصولی میخواهد.
