## ثبت ایشو #894

**عنوان:** `[improve] every paginated API endpoint clamps per_page from above only - a negative value drops the SQL LIMIT entirely and returns the whole table`

**لینک:** https://github.com/asgarimehdi/h-dashboard/issues/894

### یافته

هشت کنترلر API پیجینیشن را فقط از بالا clamp میکنند: `min($value, 100)`. مقدار منفی از `min()` رد میشود، به `paginate()` میرسد، و `Query\Builder::limit()` آن را **بیصدا نادیده میگیرد** —چون شرط انتساب `if ($value >= 0)` است. SQL بدون LIMIT تولید میشود.

```
PROBE[min((int) raw, 100)]  = -1
PROBE[per_page=-1 SQL]      => select * from "units" offset 0
PROBE[per_page=20 SQL]      => select * from "units" limit 20 offset 0

PROBE[page=1 per_page=-1]  => rows=834 perPage=-1 lastPage=834
PROBE[page=2 per_page=-1]  => rows=834 perPage=-1 lastPage=834
PROBE[page=1 per_page=100] => rows=100 perPage=100 lastPage=9
```

`offset()` با `max(0, …)` کلمپ میشود ولی `limit()` نه. `page=2` و `page=3` همان ۸۳۴ ردیف کامل را برمیگردانند، نه برش بعدی. مسیر `initial_limit` در `OrgChartController` هم چون مستقیم `->limit()` صدا میزند همین رفتار را دارد.

### اثر

- سقف صفحه‌ای که این اندپوینت‌ها مستند میکنند اصلاً سقف نیست — فقط برای مقادیر صفر به بالا کار میکند.
- `meta.per_page` مقدار منفی به کلاینت Flutter برمیگردد؛ `lastPage` برابر `total` میشود (`ceil(total / max(perPage, 1))`)، پس کلاینت به‌جای ۸۳۴ صفحه، ۸۳۴ درخواست کامل تکراری میزند.
- **نشت داده نیست**: `whereIn('unit_id', $accessibleIds)` سر جایش است. فقط سقف ردیف دور زده میشود.

دو تست موجود (`UnitApiTest::test_pagination_per_page_is_limited` و `HardwareAuditDetailTest::test_index_respects_max_per_page`) مقدار مثبت بزرگ میدهند (`1000`، `10000`) و فقط `<= 100` را assert میکنند — به همین دلیل امروز سبز است.
